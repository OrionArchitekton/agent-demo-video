## 2. Proposed optional intro and art

| Surface | Proposed treatment | Constraint |
| --- | --- | --- |
| Optional 3-4 s opening hero | Actual captured screen on a lit 3D laptop, a short camera arc finishing front-on | Preserve the spoken hook on frame 0 and the original screen sequence; no logo delay |
| Main demonstration | Match cut to the current native capture and readable captions | No perspective on dense terminal details or instructions during the proof |
| Optional surrounding plate | Brighter lit materials with restrained depth behind existing frame | New compositing must not obscure the app or turn a dark UI into unreadable glare |
| Optional thumbnail | One high-quality laptop still with a purposeful composition and large editable title | An additional candidate beside the established Codex/Imagen workflow; human choice remains |

Use the shared video-scene-kit externally in the operator's installation, never copy its private code or make it a required package dependency. Propose a new reusable `monitor_hero`/laptop preset in that kit, coordinated with the guide consumer. The shared set must accept a real screen clip and explicit 1920x1080 or 1080x1920 framing; the current kit's portrait sets do not already provide this feature. Before rendering motion, review 4-8 stills with the actual UI and hook at the most oblique angle, brightest frame and final front-on position.

The public MIT package must install, test and render without access to any private repo. Offer an explicit optional external renderer or a user-supplied prepared intro clip, with documented duration/aspect/receipt expectations. The operator can point that renderer at video-scene-kit; other users can supply an equivalent tool. No private Git URL, host alias, credentials or estate path in npm metadata, defaults or public instructions. Do not invent a mandatory service or auto-download Blender.

Blender is an optional external executable and is never bundled in the MIT package. Keep its installation outside package contents and distinguish its own license from this project's. The first public slice can consume a prepared asset; automated laptop rendering requires the separately reviewed shared-set work. Use local EEVEE for previews, optional externally gated Cycles for a hero or thumbnail. No cloud account or spend is required.

## 3. Integration and fallback

1. Once Dan starts implementation, write the domain-language behavior spec and extend the render-affecting configuration with an explicit off-by-default optional intro choice. Carry it through local/remote render inputs and manifests so remote and local results use the same asset and timing. CLI capture, TTS and authentication ownership do not move to the renderer.
2. Resolve the optional asset before ordinary segment normalization in `renderVideo`. It substitutes the first 3-4 seconds of the first eligible captured shot, then rejoins that same shot; it does not prepend time, truncate narration or create extra audio segments. Skip card-only introductions unless explicitly designed for them. The mapped screen uses those exact source frames. No invented screen states or repeated later output masquerading as the opening run.
3. Keep captions and spoken audio outside the monitor texture and above the scene. Overlay uses the existing timeline after visual substitution. An external kit compositor may be used for prepared alpha title layers, but it follows plate duration and re-encodes audio, so final parity must be checked on the actual output. Respect landscape/portrait content-aspect checks and the configured duration cap. Optional surrounding plates are the same contract, applied only to selected non-proof regions.
4. Missing renderer, unavailable Blender/kit, corrupt/short/wrong-size prepared intro or optional render failure uses the existing flat first shot and records the reason. It must not create an empty/black opening, reuse a stale successful intro or relax source-attestation and output-ownership checks. Preserve failed attempts; do not overwrite a prior completed deliverable to repair the optional look.
5. Extend the existing render report with requested/used/fallback state, renderer/asset identity and an advisory look result. Include optional asset and recipe hashes in relevant source/remote manifests. Run the external look checker after final encoding, alongside render diagnostics, never in publishing code. Missing checker reports unavailable, nonzero verdict reports failure without changing existing technical check semantics. No publishing endpoint is added.
6. Thumbnail art is an operator-invoked side artifact derived from a reviewed still, with editable title added by the existing image workflow. It does not run during ordinary MP4 generation or upload anywhere. If it fails, the existing Codex/Imagen route remains available. Do not add a motion percentage requirement to a still image.

Current video-scene-kit reference pin: `5da1461d01e60bfc0b652e9712d6f506198e07c3`. Consumers call its command interface rather than importing internals. New sets stay in its repo. If a loop is later used, every animated value must be periodic and checked through the kit-owned loop seam; at this pin the Blender runner supports `--check-loop` but the render CLI does not forward it. Qualify that separately without bypassing any GPU gate. A one-shot laptop intro needs no repeating loop.

## 4. Test seams, acceptance and one dry rehearsal

Use `renderVideo` plus its existing local/remote input and report seam for fast behavioral tests, and one decoded real MP4 for visual acceptance. Add one vertical RED to GREEN cycle per slice, after Dan starts implementation:

1. Default/off or missing-renderer configuration produces the established command/timeline behavior and zero optional tool invocation. A public clean install with no private kit/Blender succeeds. 2. Corrupt, short or wrong-aspect output fails the optional preparation and restores the legacy shot plus reason. Renderer arguments are structured, local paths are explicit and no network/credential transfer is introduced. Existing attestation/output collisions and duration/parity errors remain errors. Exercise remote serialization and content hashes with the current parity tests.
3. Actual clip substitution yields readable screen content, continuous action at the match cut, no first-frame blank and correctly placed hook/captions. A dark static fixture fails the advisory look result without suppressing existing render diagnostics. Missing checker is unavailable, never a fabricated pass.
4. Optional thumbnail emits only the requested still/candidate; disabled mode does nothing. Assert asset origin/aspect and packaging exclusions, not pixels that merely mirror the implementation. Review title readability and visual suitability manually.

Video review target is `motion`: >=30% frames in motion, >=100 contrast, >=50 mean brightness. Measure the complete final and separately the short intro and representative main-demo windows. A 4 s intro cannot rescue a 58 s dark demo; if the body still fails, retain the failed result and improve the optional lit surrounding treatment in a later approved slice. Never claim that the intro alone meets a whole-film target. Do not lower floors or select `calm` just to pass. Thumbnail motion is not applicable; contrast/brightness can be recorded descriptively while composition and readability remain human checks.

Build one complete candidate and one missing-renderer fallback, checking decode, audio/video parity, source hashes, duration cap, first-frame hook, captions and contact sheet through existing diagnostics. ## 5. Cost and optional hosts

Reference estimates at 30 fps and 1080x1920: local EEVEE 1.6 s/frame, external GPU Cycles 9-10 s/frame. The latter is the brief's gated Atlas benchmark; it is not an OSS default host or availability promise. Equal-pixel landscape and the new laptop set require timing in rehearsal. Queue, encoding, transfer and compositing are additional.

| Per demo or thumbnail | Frames | Local minutes | External GPU minutes |
| --- | ---: | ---: | ---: |
| 4-8 review stills | 4-8 | 0.11-0.21 | 0.60-1.33 |
| 4 s laptop intro | 120 | 3.2 | 18-20 |
| One thumbnail still at reference settings | 1 | 0.03 | 0.15-0.17 |
| Four thumbnail candidates | 4 | 0.11 | 0.60-0.67 |

A 3D intro is about 3.3-3.4 local minutes including the still board, or about 18.6-21.3 GPU minutes before encoding. Higher resolution/samples for key art can cost more and are not benchmarked. A reusable 20 s background would add 16 local or 90-100 GPU minutes once per accepted look, then no new Blender frames on reuse. No all-video CG render is proposed.

For the operator's shared kit, all Atlas calls must pass its current no-Elsewhere-process and free-GPU-memory gate. On refusal use local, a prepared asset or legacy fallback; never interrupt another workload. Public users opt into their own renderer explicitly. No paid compute or automatic remote work is assumed.
